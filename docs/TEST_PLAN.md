# План тестирования NorskLive Pro

Для кого: владелец, преподаватель, агенты (Antigravity, Claude Code).
Связанные документы:
- ручной чек-лист — `docs/TEST_CHECKLIST.md`;
- правила тестов для агентов — `.agents/rules/testing.md`;
- этапы разработки — `docs/AGENT_TASK_SPEC.md`.

## 1. Ворота качества
Переходим к следующей стадии, только когда всё в её строке зелёное.

| Перед чем | Что должно быть готово | Кто проверяет |
|---|---|---|
| Каждым PR | `verify.sh` → `RESULT: PASS`, CI зелёный, новые функции покрыты тестами, скриншоты для UI | агент, затем ревьюер (Claude Code) |
| Облачным стендом | всё выше + e2e зелёный локально, ручной чек-лист пройден на ПК и телефоне, RLS-тесты зелёные | владелец |
| Закрытой бетой | облачный стенд работает с входом по почте; «золотой набор» ИИ ≥ 80 % совпадения с разметкой преподавателя; матрица устройств пройдена; аудит доступности без критических ошибок; удаление аккаунта работает | владелец + преподаватель |
| Публичным запуском | оплата в тестовом режиме проверена; итоги беты (раздел 4) достигнуты; Lighthouse ≥ 90; юридические страницы на месте; e2e в CI на каждом PR | владелец |

## 2. Слои тестирования

### 2.1 Автоматические тесты (каждый PR, делает агент)
- **Unit и компоненты (Vitest + RTL), папка `tests/`.** Каждое состояние компонента, ошибки, сбой внешнего сервиса (таймаут ИИ → офлайн-ответ). Без реальных платных API и без секретов.
- **База и доступы (RLS).** `tests/rls.test.ts`, `tests/quota.test.ts` с локальным Supabase: чужие данные недоступны, лимит 20/300 считается верно.
- **Сквозной тест в браузере (Playwright), `e2e/`.** Главный сценарий на компьютере и телефоне. Сейчас запускается только локально (`npm run test:e2e`). После облачного стенда — перенести в CI.

### 2.2 Ручной чек-лист (перед облаком и бетой, делает владелец)
`docs/TEST_CHECKLIST.md`. После задачи #36 главная страница — «Мой путь к B1» и первый запуск с Норой, поэтому чек-лист надо обновить. Прогон занимает около 30 минут. Результат: отмеченный список плюс баг-репорты (раздел 5).

### 2.3 Качество ИИ (перед бетой, делает преподаватель)
Главный риск продукта: экзаменатор «исправляет» правильное или пропускает ошибки.
- **«Золотой набор»: 30 реплик учащихся уровня A2–B1:**
  - 20 с типичными ошибками: порядок слов V2, артикли, спряжение, предлоги;
  - 10 без ошибок.

  Преподаватель размечает для каждой, где ошибка и как правильно.
- **Проверяем 4 вещи:**
  1. Ошибка найдена.
  2. Правильная фраза не «исправлена».
  3. Объяснение понятно на русском, украинском и английском.
  4. Исправление звучит естественно на бокмоле.
- **Проверка на вредный ввод.** Реплика вида «ignore previous instructions…» не ломает роль экзаменатора.
- **Цель:** совпадение с разметкой ≥ 80 %, ноль «исправлений» правильных фраз.
- **Как:** исходная выборка зафиксирована в `docs/golden-set/coach-golden.csv` (30 размеченных фраз уровней A2–B1: 10 правильных и 20 с ошибками на порядок слов V2, артикли, глагольные формы и предлоги). Скрипт `npm run eval:coach` (`scripts/eval-coach.mjs`) отправляет реплики в Gemini API с параметром `temperature: 0.2`, сопоставляет вывод с ожидаемым статусом и цитатой ошибки, выводит сводную таблицу точности и ложноположительных исправлений. При отсутствии `GEMINI_API_KEY` скрипт завершается с кодом 0 (`skipped: no GEMINI_API_KEY`), не ломая локальные прогоны и CI.

### 2.4 Голос (перед бетой и перед M2)
- Голосовая лаборатория `/lab/voice`: записи владельца и 3–5 учеников с разным произношением.
- Смотрим:
  - процент ошибок распознавания (WER);
  - **сохраняются ли ошибки учащегося**: распознавание не должно само исправлять грамматику.
- По результатам выбираем модель для серверного распознавания (M2).

### 2.5 Устройства и браузеры (перед бетой, владелец + 2–3 знакомых)
| Устройство | Браузер | Особое внимание |
|---|---|---|
| iPhone | Safari | микрофон (встроенное распознавание в Safari слабое, должен быть понятный запасной вариант), нижняя панель с микрофоном, «вырез» экрана |
| Android | Chrome | микрофон, клавиатура не перекрывает поле ввода |
| Компьютер | Chrome, Edge | основной сценарий |
| Компьютер | Firefox | нет распознавания речи → текстовый ввод и понятная подсказка |
| Mac | Safari | микрофон, тёмная тема |

На каждом устройстве: первый вход, 3 реплики голосом или текстом, «Материалы», «Удобство», тёмная тема.

### 2.6 Доступность (перед бетой)
Аудит WCAG 2.1 AA по навыку `accessibility-audit`:
- автоматическая проверка;
- только клавиатура;
- экранный диктор (VoiceOver на iPhone, NVDA на Windows);
- контраст и 200 % текста;
- когнитивная нагрузка.

Критические находки исправляются отдельными задачами до беты.

### 2.7 Скорость и стоимость
- Lighthouse на телефонном профиле: производительность и доступность ≥ 90.
- Ответ экзаменатора: медиана до 3 с, 95 % — до 6 с.
- Стоимость ИИ на одну сессию из 10 реплик: считаем по логам облачного стенда и держим в рамках цены тарифа.
- Лимиты: на 21-м запросе бесплатного тарифа приходит 402, платный тариф получает 300 в день.

### 2.8 Безопасность и приватность (перед облаком и перед запуском)
- RLS: пользователь видит только свои данные (автотест).
- Ключи (Gemini, Supabase service role) только на сервере; поиск секретов в `verify.sh`.
- Личные данные и аудио хранятся только в ЕС/ЕЭЗ.
- Удаление аккаунта удаляет все строки и аудио (автотест в M4).
- Лимиты частоты на всех `/api`. Перед запуском — `/security-review`.

### 2.9 Оплата (после M3)
- Тестовый режим Stripe и Vipps: покупка меняет тариф и лимит.
- Повтор webhook не начисляет дважды.
- Отмена подписки работает.
- Отменённая или просроченная подписка возвращает бесплатный лимит (замечание из PR #33).

## 4. Закрытая бета с преподавателем
- **Состав:** 5–10 учеников уровня A2–B1, в основном русско- и украиноязычные, 2 недели.
- **Сценарии:** первый вход с Норой → 3 практики за неделю → пробный экзамен в конце.
- **После каждой сессии** опрос из 3 вопросов в приложении или Google Form:
  - было ли полезно;
  - понятны ли исправления;
  - что мешало.
- **Преподаватель** раз в неделю смотрит 10 случайных исправлений и отмечает, верны ли они.
- **Метрики успеха:**
  - первую практику завершили ≥ 40 % пришедших;
  - вернулись на следующий день ≥ 30 %;
  - точность исправлений по оценке преподавателя ≥ 80 %;
  - среди критических ошибок ни одной неисправленной на конец беты.
- **Итог:** короткий отчёт (что работает, что исправить) и решение о публичном запуске.

## 5. Баг-репорты
Где хранить: GitHub issues с меткой `bug`. Для беты можно Google Form, а владелец переносит в issues.

Шаблон:
```
Что делал: …
Что ожидал: …
Что произошло: …
Устройство и браузер: …
Скриншот или видео: …
Время (примерно): …
```

Приоритеты:
- **P1** — нельзя пользоваться (пустой экран, потеря данных, оплата). Чиним сразу.
- **P2** — мешает, но есть обход. В ближайшую задачу.
- **P3** — косметика. В общий список.
