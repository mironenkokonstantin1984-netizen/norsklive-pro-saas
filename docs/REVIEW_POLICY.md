# Политика ревью

Адаптация подхода команды Claude Code («How the Claude Code team does code review», 15.10.2026)
под наш проект. Цель: **минимум времени владельца на каждое изменение — без роста откатов и
инцидентов.** Время владельца здесь самый дорогой ресурс; читает код в основном машина.

Правила для ревьюера — `REVIEW.md`. Правила для агента — `AGENTS.md` и `.agents/`.

## Слои проверки (от дешёвого к дорогому)
| # | Слой | Кто | Что блокирует |
|---|---|---|---|
| 1 | Проверка до PR: `verify.sh`, self-review (`code-review` skill), скриншоты | агент | красный `verify.sh` |
| 2 | CI: lint, typecheck, vitest, build | GitHub Actions | красный CI |
| 3 | Ревью Claude Code: критерии задачи, e2e ×2, скриншоты, код | Claude Code | замечания «Blocking» |
| 4 | **Ворота `review-gate`**: нет `✅ … accepted` на этот коммит — нет зелёного статуса | GitHub Actions | статус `review-gate` не `success` |
| 5 | Решение владельца по уровню риска (ниже) | владелец | Merge |
| 6 | После слияния: Vercel Preview → Production, откат одной кнопкой | владелец | — |

Ворота (слой 4) закрывают инцидент №1 из `docs/INCIDENTS.md`: PR был слит до окончания ревью.
Чтобы они реально блокировали Merge, владелец один раз включает их в защите ветки (см. ниже).

## Уровни риска (задаёт изменение, а не автор)
| Уровень | Примеры у нас | Что нужно перед Merge |
|---|---|---|
| Низкий | тексты, документация, таблицы слов/сценариев, стили без логики | зелёный CI + `✅ accepted` |
| Средний | обычные экраны и логика практики, тесты | то же + владелец смотрит скриншоты в PR |
| Высокий | `/api/coach`, промпты, TTS-адаптеры, ключи и env, авторизация, Supabase и RLS, `.github/workflows`, оплата, данные учеников | то же + владелец сам открывает превью и проходит сценарий; отдельный проход `security-review` |

Путь из высокого уровня всегда требует человека: список закреплён в `.github/CODEOWNERS`.
Одобрение бота никогда не заменяет решение владельца.

## Ревью обязано заканчиваться
Сходимость важнее числа раундов. Правила (дублируют `REVIEW.md`):
- раунд 1 — полный; со 2-го — только новый diff и ещё открытые пункты;
- замечание называет **класс** ошибки, чтобы агент исправил все места, а не одну строку;
- без повторов уже написанных замечаний;
- после 3-го раунда агент останавливается и пересматривает подход, а не добавляет раунд 4;
- `✅ accepted` относится к одному коммиту; новый коммит требует новой проверки.

## Инциденты становятся тестами
Каждый откат, исправление «вдогонку» или ошибку, замеченную владельцем на сайте, записываем в
`docs/INCIDENTS.md`: что случилось, какой слой должен был поймать, что добавили (тест, строку в
`REVIEW.md`, проверку). Без добавленной проверки инцидент не считается закрытым.
Для тренера дополнительно растёт золотой набор `docs/golden-set/coach-golden.csv`.

## Что считаем (раз в месяц)
- раундов ревью на PR (цель: медиана ≤ 2, ни одного ≥ 5);
- сколько PR слито до `✅ accepted` (цель: 0);
- откаты и инциденты на 10 слитых PR (страховочная метрика: не должна расти).

## Единоразовая настройка владельцем (GitHub)
Settings → Branches → Branch protection rule для `master`:
1. Require status checks to pass before merging → добавить `lint-and-test` и `review-gate`.
2. Require branches to be up to date — по желанию.
Без этого `review-gate` только показывает красную/жёлтую точку, но не запрещает Merge.
